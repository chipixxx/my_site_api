Форматы обмена данными: JSON и XML

Роль форматов сериализации в веб-разработке

В современной веб-разработке серверная и клиентская части приложения чаще всего создаются на совершенно разных языках программирования и работают на независимых платформах. Например, серверный бэкенд может функционировать на Node.js, Go, Python или Java, тогда как клиентом выступает браузер с JavaScript или мобильное приложение на Swift и Kotlin. Чтобы эти гетерогенные системы могли беспрепятственно обмениваться объектами, массивами и структурами данных, требуется общий, платформонезависимый язык сериализации.

Исторически двумя ключевыми форматами текстового обмена сообщениями в сети стали XML (eXtensible Markup Language) и JSON (JavaScript Object Notation). На заре развития веб-сервисов в 1990-х и начале 2000-х годов безусловным лидером был XML, являвшийся основой стека SOAP и корпоративных информационных систем. Однако с развитием концепции Web 2.0, архитектурного стиля REST и одностраничных веб-приложений (SPA) формат JSON вытеснил XML и стал отраслевым стандартом для веб-API.

Формат JSON: простота, скорость и лаконичность

JSON (JavaScript Object Notation) - текстовый формат обмена данными, базирующийся на подмножестве синтаксиса определения объектов в JavaScript (стандарт ECMA-262), но полностью независимый от какого-либо языка. Он был популяризирован в начале 2000-х годов Дугласом Крокфордом (Douglas Crockford) как легкая и понятная человеку альтернатива громоздким форматам на основе тегов.

Структура JSON строится всего на двух универсальных конструкциях:

  • Коллекция пар «ключ - значение»: в разных языках это реализуется как объект, словарь (dictionary), ассоциативный массив или хэш-таблица. Ключ всегда является строкой в двойных кавычках.
  • Упорядоченный список значений: список или массив элементов (array), обрамляемый квадратными скобками [].

JSON изначально поддерживает типизацию на базовом уровне: строки (string), числа (числа с плавающей точкой и целые), логические константы (true, false), значение null, а также вложенные объекты и массивы. Благодаря этому парсинг в браузере осуществляется нативно и мгновенно с помощью встроенного метода JSON.parse(), а обратная сериализация - через JSON.stringify().

Пример данных в формате JSON

Ниже представлен пример описания карточки товара в интернет-магазине:

{
  "id": 4092,
  "sku": "KB-MECH-RGB-01",
  "title": "Механическая клавиатура HyperPro 87",
  "inStock": true,
  "price": {
    "amount": 7990.50,
    "currency": "RUB",
    "discountPercent": 15
  },
  "categories": ["Периферия", "Клавиатуры", "Гейминг"],
  "specifications": {
    "switchType": "Red Linear",
    "connection": "USB Type-C",
    "backlight": "RGB per-key",
    "weightGrams": 850
  },
  "rating": 4.85,
  "reviewsCount": 42
}

Формат XML: расширяемость и строгая стандартизация

XML (eXtensible Markup Language - «расширяемый язык разметки») - рекомендация консорциума W3C, созданная для описания и структурирования данных посредством иерархических тегов. В отличие от HTML, где набор тегов жестко фиксирован и служит для отображения внешнего вида элементов в браузере, в XML разработчик сам создает необходимые теги, отражающие семантику передаваемой информации.

Сильная сторона XML заключается в его колоссальной экосистеме сопутствующих технологий:

  • XML Schema (XSD) и DTD: мощнейшие средства описания структуры и строгой валидации типов данных, позволяющие проверять корректность входящих файлов еще до того, как они попадут в бизнес-логику приложения;
  • Пространства имен (Namespaces): атрибут xmlns предотвращает конфликты имен элементов при объединении документов различных стандартов в один XML-пакет;
  • XPath и XQuery: стандартизированные языки запросов для выборки и фильтрации узлов в сложных древовидных XML-структурах;
  • XSLT (Extensible Stylesheet Language Transformations): функциональный язык декларативного преобразования документов из формата XML в HTML, PDF или другие форматы данных.

Пример тех же данных в формате XML

Аналогичная карточка товара, описанная на языке XML с использованием вложенных тегов и атрибутов:

<?xml version="1.0" encoding="UTF-8"?>
<product id="4092" sku="KB-MECH-RGB-01" inStock="true">
  <title>Механическая клавиатура HyperPro 87</title>
  <price currency="RUB" discountPercent="15">7990.50</price>
  <categories>
    <category>Периферия</category>
    <category>Клавиатуры</category>
    <category>Гейминг</category>
  </categories>
  <specifications>
    <spec name="switchType">Red Linear</spec>
    <spec name="connection">USB Type-C</spec>
    <spec name="backlight">RGB per-key</spec>
    <spec name="weightGrams">850</spec>
  </specifications>
  <rating>4.85</rating>
  <reviewsCount>42</reviewsCount>
</product>

Сравнительный анализ: JSON против XML

Оба формата отлично справляются с задачей иерархического представления данных, однако обладают принципиально разными инженерными характеристиками, ресурсоемкостью и сферами применения:

Критерий сравнения JSON (JavaScript Object Notation) XML (eXtensible Markup Language)
Читаемость Очень высокая. Лаконичный синтаксис на основе фигурных и квадратных скобок, интуитивно понятен разработчикам и удобен для восприятия человеком. Средняя. Большое количество открывающих и закрывающих тегов создает визуальный шум и затрудняет быстрое чтение человеком больших структур.
Размер данных Минимальный. Отсутствие избыточных закрывающих тегов обеспечивает компактный размер полезной нагрузки и экономию интернет-трафика. Значительный. Повторяющиеся имена тегов и служебные атрибуты увеличивают объем передаваемого файла в среднем на 30-50% по сравнению с JSON.
Поддержка типов Встроенная базовая типизация: строки, числа, логический тип (булево), массивы, объекты и null. Все значения по умолчанию являются текстом. Строгая типизация возможна только при подключении внешней схемы валидации XSD (XML Schema).
Использование в API Абсолютный лидер в современных веб-технологиях: REST API, GraphQL, WebSockets, микросервисы, мобильные клиенты и базы данных NoSQL. Применяется преимущественно в протоколах SOAP/WSDL, корпоративных шинах данных (ESB), банковских шлюзах и госсервисах.
Схема валидации Поддерживается через стандарт JSON Schema, однако на практике валидация чаще выполняется на уровне моделей языка программирования (DTO). Чрезвычайно развитая и мощная система строгой формальной валидации на базе XSD (XML Schema Definition) и DTD на уровне парсера.
Поддержка комментариев Не поддерживается официальной спецификацией RFC 8259 во избежание неоднозначностей при парсинге данных. Полная нативная поддержка комментариев с помощью стандартного синтаксиса <!-- комментарий -->.

Выводы: когда и какой формат использовать?

Выбор между JSON и XML определяется архитектурными требованиями проекта, целевой аудиторией сервиса и необходимостью интеграции со сторонними платформами:

Выбирайте JSON, если:

  • Вы разрабатываете современное клиент-серверное веб-приложение (SPA на React, Vue, Angular) или мобильное приложение;
  • Вы создаете публичный или внутренний RESTful API;
  • Критична скорость парсинга, низкое потребление памяти и минимальная задержка при передаче пакетов по сети;
  • Хранилищем данных выступает документоориентированная СУБД (например, MongoDB, CouchDB или PostgreSQL с полями типа JSONB).

Выбирайте XML, если:

  • Требуется интеграция с унаследованными (legacy) корпоративными системами, банковскими шлюзами или государственными реестрами, работающими по протоколу SOAP;
  • Обязательна жесткая валидация структуры и форматов сложных документов по контрактам XSD до передачи данных в вычислительный контур;
  • Формат используется для разметки документов смешанного типа (где текст перемежается тегами форматирования), создания офисных файлов (OpenXML, DOCX, XLSX) или векторной графики (SVG);
  • Необходима трансляция данных между различными форматами на лету с использованием механизмов XSLT.
