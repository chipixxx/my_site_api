REST API - архитектурный стиль

Что такое REST и почему он стал стандартом?

REST (Representational State Transfer - «передача состояния представления») - это архитектурный стиль взаимодействия компонентов распределенного веб-приложения, предложенный в 2000 году Роем Филдингом (Roy Fielding), одним из ключевых авторов спецификации протокола HTTP. В отличие от жестких протоколов удаленного вызова процедур (таких как SOAP или RPC), REST представляет собой не строгий стандарт или протокол, а набор принципов и архитектурных ограничений, благодаря которым веб-сервисы становятся быстрыми, надежными, масштабируемыми и удобными для модификации.

Веб-сервисы, спроектированные с соблюдением требований REST, называют RESTful. Главная идея стиля заключается в том, что вся информация в системе представляется в виде отдельных ресурсов (например, пользователь, заказ, статья, комментарий). Каждый ресурс обладает уникальным идентификатором - URL (Uniform Resource Locator). Клиенты взаимодействуют с ресурсами, отправляя стандартные HTTP-запросы и получая в ответ представление ресурса в формате JSON или XML.

Ключевые принципы архитектуры REST

Чтобы сервис можно было считать истинно RESTful, он должен удовлетворять шести фундаментальным ограничениям (constraints), сформулированным Роем Филдингом:

  1. Клиент-серверная модель (Client-Server Architecture): Четкое разделение ответственности между пользовательским интерфейсом (клиентом) и хранением данных с бизнес-логикой (сервером). Клиент не заботится о структуре базы данных или алгоритмах хранения, а сервер не формирует верстку интерфейса. Это позволяет независимо развивать и масштабировать веб-интерфейс, мобильные приложения и серверный бэкенд.
  2. Отсутствие состояния (Statelessness): Сервер не хранит информацию о текущем состоянии сессии клиента между запросами. Каждый HTTP-запрос от клиента должен быть самодостаточным - он обязан содержать все параметры, заголовки и учетные данные (например, JWT-токен или API-ключ), необходимые серверу для успешной авторизации и обработки запроса. Это гарантирует надежность и позволяет легко балансировать трафик между десятками серверов.
  3. Кэшируемость ответов (Cacheable): Каждый ответ сервера должен быть явно или неявно помечен как кэшируемый либо некэшируемый при помощи HTTP-заголовков (Cache-Control, ETag, Expires). Кэширование на стороне браузера или промежуточных прокси-серверов (CDN) уменьшает задержки сети и кардинально снижает нагрузку на базу данных.
  4. Единый унифицированный интерфейс (Uniform Interface): Фундаментальный принцип, обеспечивающий простоту и предсказуемость API. Он строится на четырех подпунктах:
    • Идентификация ресурсов: каждый ресурс адресуется собственным URI (например, /api/v1/articles/42);
    • Манипуляция ресурсами через представления: клиент получает снимок данных (JSON/XML) и может модифицировать ресурс, отправляя обратно обновленное представление;
    • Самоописываемые сообщения: каждый запрос и ответ содержат метаданные (MIME-тип Content-Type, кодировку), объясняющие, как интерпретировать данные;
    • HATEOAS (Hypermedia As The Engine Of Application State): ответы сервера могут содержать гиперссылки на связанные действия и ресурсы, позволяя клиенту динамически исследовать API.
  5. Многоуровневая система (Layered System): Архитектура системы может состоять из нескольких уровней: балансировщиков нагрузки, кэширующих серверов, шлюзов безопасности (API Gateway) и серверов баз данных. При этом клиент взаимодействует с шлюзом так, будто общается напрямую с конечным сервером, не зная деталей внутренней инфраструктуры.
  6. Код по требованию (Code on Demand - опционально): Сервер может временно расширить возможности клиента, передавая исполняемый код (например, скрипты JavaScript для валидации на стороне клиента). Это единственное необязательное ограничение REST.

Методы HTTP и их семантика в RESTful API

В RESTful сервисах действия над ресурсами выражаются не именами URL (например, не стоит делать /getUser или /deleteUser), а стандартными глаголами протокола HTTP. В таблице ниже представлены основные методы, их свойства и практические примеры:

Метод Назначение Свойства Пример эндпоинта Описание действия
GET Получение ресурса или коллекции ресурсов Безопасный, Идемпотентный GET /api/v1/users/15 Возвращает информацию о пользователе с ID 15. Не изменяет состояние сервера.
POST Создание нового подчиненного ресурса Небезопасный, Неидемпотентный POST /api/v1/users Создает нового пользователя на основе переданного тела запроса. Возвращает статус 201 Created.
PUT Полная замена существующего ресурса Небезопасный, Идемпотентный PUT /api/v1/users/15 Полностью перезаписывает данные пользователя 15 новыми значениями всех полей объекта.
PATCH Частичное изменение полей ресурса Небезопасный, Неидемпотентный* PATCH /api/v1/users/15 Обновляет только указанные поля (например, смену адреса email или статуса активности).
DELETE Удаление указанного ресурса Небезопасный, Идемпотентный DELETE /api/v1/users/15 Удаляет запись о пользователе с ID 15 из базы данных. Повторный вызов возвращает 404 Not Found или 204 No Content.

Примечание: Метод считается безопасным, если его выполнение не приводит к изменению состояния на сервере. Метод считается идемпотентным, если повторные одинаковые запросы дают точно такой же результат, как и однократный запрос.

Пример взаимодействия: REST-запрос и ответ сервера

Рассмотрим практический сценарий создания новой статьи в блоге через REST API. Клиент отправляет POST-запрос с полезной нагрузкой в формате JSON, передавая токен авторизации в заголовке Authorization:

1. HTTP-запрос от клиента (Request)

POST /api/v1/articles HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
Content-Type: application/json; charset=utf-8
Accept: application/json

Рекомендации по проектированию чистого REST API

Грамотно спроектированный API интуитивно понятен разработчикам и прост в интеграции. Профессиональные команды придерживаются следующих правил:

  • Существительные во множественном числе для именования сущностей: используйте /users, /orders, /products вместо глаголов в пути URL.
  • Иерархия для вложенных ресурсов: для получения комментариев конкретной статьи используйте путь /articles/108/comments.
  • Фильтрация, сортировка и пагинация через query-параметры: параметры запроса передаются через знак вопроса, например: /articles?category=backend&sort=-createdAt&page=1&limit=10.
  • Корректное использование статус-кодов HTTP: группа 2xx (успех), 4xx (ошибки клиента, такие как 400 Bad Request или 401 Unauthorized), 5xx (внутренние сбои сервера).
  • Версионирование API: обязательно указывайте версию интерфейса в пути URL (например, /api/v1/), чтобы будущие изменения не ломали работу существующих клиентских приложений.
